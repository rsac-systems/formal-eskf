## Scope and precautions

- Read all **144 canonical requirement bodies**, their parent/Uses allocations
  and the three architecture inputs listed below. Include shared math/core,
  runtime, PX4 and host replay. Every requirement in this baseline is **Draft**.
- Start from requirements, then examine boundary assumptions and interactions.
  Consider startup, operation, degraded operation, source change, recovery,
  reset/rebase and shutdown where applicable. A hypothetical failure is not a
  demonstrated code defect; implementation/evidence inspection is later work.
- Keep loss, wrong-but-plausible output, stale output, misleading confidence and
  failed recovery distinct. Required guards are analysis inputs, not credited
  mitigations. A positive test or proof under premises does not establish those
  physical premises or a consumer response.
- Retain conditional variants: INS/AHRS, scalar/backend, dense/generated,
  exact/approximate, direct/aggregate, rate and sensor-feature choices. References
  describe applicability, not support or qualification for every combination.
- The flight-related boundary ends at estimate/status/reset consumers. Vehicle
  consequences are conditional. Replay-only failures are assurance contributors;
  do not invent an in-flight function for a host-only requirement.
- No severity, probability, DAL/SIL, FMECA/RPN, mitigation effectiveness,
  cut sets, risk acceptance or certification conclusion is assigned. No complete
  fault tree, code audit, formal proof or exhaustive physical hazard search is claimed.

Deduplication uses function/item, boundary, context and effect. Shared math/failure
constraints contribute to named effects rather than becoming separate aircraft
hazards. Parent composition remains visible in FMEA-C028 and the relevant sensor
families. Different method views intentionally link the same causal chain.
FMEA records the direct requirement links once. FHA/FTA inherit the contributing
requirements through their linked FMEA families; the ledger below records those
dispositions. This avoids duplicating long requirement lists in every view and
does not assert independent or sufficient causation. Follow a FMEA link to reach
its requirements and both other analysis views.

GNSS-datum-WMM dependencies, gravity/prediction reuse, regularization/recovery,
multi-owner resets, configuration/rate and resource contention. No candidate IDs
have been retired in this first edition. Old illustrative H-/SC-/U- proposals and
provisional severity labels in other analysis drafts are not adopted here.

## Open inputs and follow-up

| ID | Missing input / review boundary | Required follow-up |
|---|---|---|
| G-01 | Vehicle, mission and consumer contract | No single vehicle/mission, flight phase envelope, permissible errors, response times or demonstrated fallback is adopted here. Identify consumer modes, landing/terrain responsibilities and required services before severity or risk decisions. |
| G-02 | Physical and numerical qualification | Thresholds/noise, synchronization, gravity/rest assumptions, magnetic interference, geographic envelope, mixed-precision error and tracking stability need accepted profile bounds. A contract or finite computation does not supply those bounds. |
| G-03 | Target timing and resource evidence | Board/clock/compiler/OS, queue load, input bursts, complete stack/backing storage and dependency allocation/locking must be bound to declared deadlines. Fixed capacities and host runs do not establish real-time acceptance. |
| G-04 | External premises and common dependencies | Drivers, calibration writers, land/rest detector, GNSS integrity, clock synchronization, WMM provider, controllers and platform resources are boundary dependencies. | G-05 | Scenario-to-implementation/evidence review | These are hypothesized contract-level failures, not detected code defects. Detailed analysis must locate implementations/consumers, inspect current guards and evidence scope, and determine residual propagation. No proof status is inferred from requirement prose. |
| G-06 | Profiles and change impact | INS/AHRS, exact/approximate, dense/generated, scalar/backend, direct/aggregate, feature and rate variants are considered conditionally, not exhaustively multiplied or qualified. Enumerate supported combinations before detailed deployment analysis; re-review dependencies even when requirement hashes are unchanged. |
| G-07 | Assurance and data threats | Replay preprocessing, correlated reference, shared test oracle, stale generated artifacts and evidence/configuration mismatch can invalidate qualification. Several parent decomposition rows describe targets as pending while child text reports implementation; approval, implementation and qualification must be reconciled separately. This inventory changes none of them. |
| G-09 | Inventory completeness limit | All canonical requirement files have been read and mapped, but clause-level exhaustiveness, every physical scenario and source-level failure modes are not established. Validate the candidate set with domain/consumer review and future anomalies. Future detailed analysis may split or add stable IDs. |

First review the scenario scope and G-08 interpretation. Then choose a concrete
deployment and consumers, resolve its premises/limits, and prioritize detailed
FHA/FMEA/FTA. Earlier detailed-template and record-storage proposals remain
separate Draft work; this inventory adopts neither a database nor their
detailed-analysis fields.
Do not assign artificial numbers merely to fill an analysis template.

## Updating a baseline

Run the project skill's checker **before** refreshing fingerprints:

```bash
python3 .agents/skills/inventory-safety/scripts/check_inventory.py --repo .
```

It detects missing/new/changed requirement inputs, changed supplemental inputs,
duplicate/unknown scenario IDs and inconsistent requirement-to-scenario accounting.
It does not validate causal reasoning or prove an analysis remains applicable.
Review changes with affected parents, dependencies, callers, enabled profiles and
external assumptions; unchanged requirements can still be affected by a new
sensor, code/configuration change, environment or field anomaly. This inventory
does not fingerprint every implementation/dependency or authorize release reuse.
Retain IDs, add new ones without renumbering, and record explicit supersession
when splitting/retiring a candidate. Update fingerprints only after reviewing
the affected content. Later risk decisions and evidence belong in detailed records.
